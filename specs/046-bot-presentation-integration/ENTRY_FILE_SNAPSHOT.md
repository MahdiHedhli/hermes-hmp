# Original recipe-derived entry and wrapper file snapshot

Status: bounded source snapshot implemented and independently reviewed. This is
file/origin DATA under the existing trusted-installed-runtime premise, not
executed-byte attestation, operator approval, hostile same-UID isolation or
native/key authority. The full character-image runtime remains unfinished.

## Inputs, table and path ownership

hmp_startup.entry_files.EntryFileSnapshotOwner.verify accepts only actual original
GatewayEntryOwner, GatewayRecipeOwner and GatewayPackageOwner instances. Their
original bindings must share the same activation and recipe. Pure vacancy checks
precede fresh callbacks so a duplicate cannot poison original historical facts.
The entry bytes come from the recipe's original immutable entry document; no
caller-supplied replacement payload, digest, root or numeric budget is accepted.

The canonical closed entry document has exactly schema1, kindHMP_GATEWAY_ENTRY,
generation, package, entries and wrapper. Generation matches the original recipe.
Package equals the actual entry module and verifier module directory, separated
from private selection storage. The existing bounded, sorted, unique file-table
projection is reused as DATA; the verifier independently binds the root and pin.
The actual entry/verifier files must be declared. Loaded entry-package module/
spec/loader/search-path observations must correspond to declared files.

Wrapper has exactly path/size/sha256. Path matches the original observed main file;
private configuration names/storage are excluded. It receives the same no-follow,
regular single-link owner/mode/size/hash/EOF and stable metadata checks as entry
files. When inside the entry tree, it must already have identical expected fields
and is read once as that exact table row. Conflicting duplicates refuse. A wrapper
outside the tree gets its own read and before/after owned ancestry/leaf metadata.
No URL, redirect, arbitrary profile path or parsed command is supported.

## Owned IO and combined accounting

StartupArtifactOwner now separates retain and complete. Retention attaches the
partial original owner/scope/count before any tree IO. Completion retains its
one-shot attempt before native context/currentness effects; an initial exception
or partial failure stays failed and cannot be restored/retried. Wrong acquisition
context is a failed completion, distinct from read-only historical queries.
Legacy observe and expected-file facts remain compatible. New actual hash receipts
and final actual count allocations are retained in an independent publication.

retain_from_package derives its source only from the actual original recipe-backed
plugin owner/count and prior expectations. Combined file/byte limits include the
five recipe documents, plugin files, entry files and any distinct wrapper. There
is no scalar count parameter or fresh-budget reset. Earlier private selection IO,
subsequent dependency/interpreter artifacts and full startup composition remain
required; this is not a claim of complete whole-factory accounting.

The partial file owner owns all metadata/hash descriptors. Two complete no-follow
trees before/after hashing join actual leaf, directory and ancestor identities to
the actual hash receipts. External wrapper metadata is checked on both sides,
including actual hash-time identity. Same-name/same-bytes inode replacement refuses.
Scandir acquisition/next/close is attributed before effects; all known held handles
receive their owned close attempt even on failure. Lost acknowledgement retains
unknown state, never a retry or manufactured closure. Fixed primitive name and
boolean identity checks reject foreign getter/truthiness dispatch.

Fresh entry/recipe/plugin checks are followed by pure original joins after the last
callback, including invocation/module provenance. Publication rejoins the original
IO owner, actual hash/count fact, parent inputs and closed descriptor/scan facts.
This is a bounded filesystem observation, not an atomic filesystem, execution or
OS-loader attestation. Future imports/runtime policy and installed control flow
remain separate requirements before any credential/native publication.
