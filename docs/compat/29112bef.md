# Hermes `v2026.8.31` read-adapter investigation

Source: exact tag `v2026.8.31`, commit
`29112bef099274229cadff79cdff7bf7b99c4b77`. The source was exported from
a clean clone into an isolated fixture on 2026-09-29. This document describes
the adapter work still needed; it does **not** qualify Bot Chat on this tag.

## Observed behavior

The existing HMP read fingerprint cannot identify this source: 8 of its 16
listed bridge paths did not exist yet. The missing paths are
`gateway/platforms/_shared.py`, `gateway/platforms/event.py`,
`gateway/run_adapters.py`, `gateway/run_profile_reconcile.py`, and the four
`hermes_state_*` split modules. The exact-tag fixture verifies this list and
that HMP does not import the unqualified read bridge. A separate scratch-home
boot of the full gateway connected HMP. A certificate-pinned client received
`200` from `/hmp/v1/ready` and `503 hermes_build_unsupported` from `/hmp/v1/bots`.
Neither check exercised a phone or qualified a Bot Chat read.

An additional isolated invocation of the tag's real
`GatewayRunner._resolve_profile_home_for_source` used a source with an explicit
nonexistent profile and a scratch `HERMES_HOME`. It resolved to that scratch
root, confirming the source-level fallback behavior. No `state.db` existed in
the scratch home. This invocation proves the unsafe lookup behavior, not that
HMP called it or exposed data; the current compatibility gate still refuses
the read route.

The old source contains several predecessor interfaces:

The current read bridge now checks the live served set before consulting its
profile-home resolver. A regression test makes an unserved name point at a
served profile's fake home and verifies that a session read is refused before
the resolver runs. This closes that fallback class in the current bridge; it
does not qualify the old Hermes resolver or its authorization behavior.

## Qualification required before enabling Bot Chat

1. Add an adapter selected only by a reviewed exact build identity. Keep the
   current 16-file fingerprint and current-build behavior unchanged; use a
   separate old-source file list and dependency probe. A version string or
   signature match is not authorization evidence.
2. Build a profile resolver that starts from the running gateway's effective
   served set, validates the requested profile name and existence, and checks
   its home against that exact profile. Refuse every missing, tombstoned,
   unserved, mismatched, or route-rejected profile. Never call the old
   `_resolve_profile_home_for_source` as the authority for HMP reads.
3. Prove authorization against the old gateway's actual HMP ingress for the
   default and a secondary profile. Include per-bot denial, cross-profile
   denial, allow-all refusal, and transport-versus-runtime scope cases.
4. Use only an existing profile `state.db` opened read-only. Verify that
   roster, conversation lookup, history, compaction lineage, and session
   browsing neither create a session nor mutate a database or its sidecars.
   Refuse missing or unreadable state explicitly.
5. Test a real isolated gateway with a paired client and two independently
   configured profiles. Only after read and authorization tests pass may an
   exact-tag read-compat entry be added. Send, jobs, model writes, and prompt
   control require separate qualification and remain closed by default.

Until these gates pass, independent device pairing and explicit
`hermes_build_unsupported` responses are the supported behavior on this tag.
