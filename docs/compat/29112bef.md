# Hermes `v2026.8.31` read-adapter investigation

Source: exact tag `v2026.8.31`, commit
`29112bef099274229cadff79cdff7bf7b99c4b77`. The source was exported from
a clean clone into an isolated fixture on 2026-09-29. This document describes
the adapter work still needed; it does **not** qualify Bot Chat on this tag.

## Observed behavior

The existing HMP read fingerprint cannot identify this source: 8 of its 16
listed bridge paths did not exist yet. The missing paths are
`gateway/platforms/_shared.py`, `gateway/platforms/event.py`,
`gateway/run_adapters.py`, `gateway/run_profile_reconcile.py`, and the four
`hermes_state_*` split modules. The exact-tag fixture verifies this list and
that HMP does not import the unqualified read bridge. A separate scratch-home
boot of the full gateway connected HMP. The repeatable two-profile gateway
fixture now confirms that both profiles are served, a certificate-pinned
synthetic client completes HMP pairing, and `/hmp/v1/bots` still returns
`503 hermes_build_unsupported`. The fixture uses a disposable home and stops
the gateway process. It does not exercise a physical phone or qualify a Bot
Chat read.

Run `server/tests/integration/test_pantheon_gateway_pairing.py` with
`HMP_PANTHEON_CLONE` pointing at a clone containing the immutable tag and
`HMP_PANTHEON_RUNTIME_PYTHON` pointing at a disposable interpreter with the
tag's frozen base dependencies and HMP's declared runtime dependencies. The
fixture gives the old CLI `--force` only inside its checked scratch home
because its launchd guard can see an unrelated supervised gateway on the
owner's machine.

An additional isolated invocation of the tag's real
`GatewayRunner._resolve_profile_home_for_source` used a source with an explicit
nonexistent profile and a scratch `HERMES_HOME`. It resolved to that scratch
root, confirming the source-level fallback behavior. No `state.db` existed in
the scratch home. This invocation proves the unsafe lookup behavior, not that
HMP called it or exposed data; the current compatibility gate still refuses
the read route.

The old source contains several predecessor interfaces:

The current read bridge now checks the live served set before consulting its
profile-home resolver. A regression test makes an unserved name point at a
served profile's fake home and verifies that a session read is refused before
the resolver runs. This closes that fallback class in the current bridge; it
does not qualify the old Hermes resolver or its authorization behavior.

The exact-tag fixture also invokes `SessionStore._generate_session_key` without
constructing a store. For a standalone named profile, it uses the legacy
`agent:main` namespace; for a multiplexed profile, it uses the named profile
namespace. An old read adapter must ask that store for the key (or reproduce
both modes with exact-build tests), rather than always passing the profile to
`build_session_key` as the current bridge does.

An unwired `pantheon_profiles.existing_session_id` primitive now uses that old
store method and `lookup_by_session_key` for an **existing** session. It refuses
an unserved profile, mismatched or rejected source, and malformed key or entry;
an absent entry remains distinct from an invalid entry. An exact-tag scratch
probe verifies both standalone and multiplexed namespaces through the real
old key generator without creating a session. This is not an authorization
gate: `build_source` can stamp the primary profile when no route matched. HMP
must independently prove a genuine route and the same per-user authorization
decision as Hermes ingress before using this primitive for Bot Chat reads.

In the same isolated tag fixture, `SessionDB(path, read_only=True)` refused a
missing database without creating it. The fixture now seeds two scratch
profile databases with the same session ID and different synthetic message
content. The strict profile-home resolver selects each database; the old
read-only `SessionDB.get_messages` returns only that profile's content, and
the database and sidecar file hashes are unchanged after both reads. This
proves a narrow storage and profile-selection primitive under the fixture's
SQLite mode. It does not prove a live gateway's routing, canonical Bot Chat
lookup, compression lineage, or behavior under every WAL configuration.

A separate, currently **unwired** `pantheon_profiles.py` resolver now uses the
old tag's real `profiles_to_serve`, `get_active_profile_name`, profile existence,
and home-match helpers. In the exact-tag scratch fixture it returns only the
default and allowlisted named profile, refuses an unknown profile rather than
falling back to root, waits for per-profile pairing-store registration, and
handles a named primary omitted from the secondary allowlist. Unit tests also
refuse malformed gateway mode, mismatched homes, and named-home symlinks that
could alias another profile. This is groundwork for item 2 below, **not**
evidence that Bot Chat authorization or history is qualified.

An optional exact-tag ingress probe runs under the tag's frozen base Python
dependencies plus HMP's declared runtime dependencies in a disposable
interpreter. It constructs an isolated two-profile `GatewayRunner` with the
old `HmpAdapter.build_source` and real per-profile `PairingStore` approvals.
With explicit profile routes, the adapter stamps the primary and named
profiles; an unserved route gets `profile_route_rejected`, and the real old
`GatewayRunner._handle_message` drops that source before authorization or
session setup. Without a matching
route, a source carrying the named `scope_id` and `guild_id` still has no
`profile` stamp. The probe accepts only the grants in their respective
profiles, denies cross-profile and never-enrolled users, and confirms that
the stamped transport authorization home takes precedence over the routed
runtime's secret scope. A synthetic allow-all runtime scope admits its canary
when the transport stamp is absent, so a future HMP read adapter must test
and refuse permissive access in both scopes. The probe does not run a full
gateway, pair a phone, or qualify old-tag Bot Chat reads.

## Qualification required before enabling Bot Chat

1. Add an adapter selected only by a reviewed exact build identity. Keep the
   current 16-file fingerprint and current-build behavior unchanged; use a
   separate old-source file list and dependency probe. A version string or
   signature match is not authorization evidence.
2. Build a profile resolver that starts from the running gateway's effective
   served set, validates the requested profile name and existence, and checks
   its home against that exact profile. Refuse every missing, tombstoned,
   unserved, mismatched, or route-rejected profile. Never call the old
   `_resolve_profile_home_for_source` as the authority for HMP reads.
3. Extend the paired two-profile gateway fixture beyond the current closed
   read gate. Prove that each requested bot has a genuine matching route stamp
   and the same authorization decision as ingress for both primary and
   secondary profiles. Refuse missing routes, cross-profile grants, unserved
   profiles, and allow-all in either the transport or runtime scope. The
   isolated `build_source`/`PairingStore` probe covers only part of this gate.
4. Use only an existing profile `state.db` opened read-only. Verify that
   roster, conversation lookup, history, compaction lineage, and session
   browsing neither create a session nor mutate a database or its sidecars.
   Refuse missing or unreadable state explicitly.
5. The real isolated gateway and paired synthetic client now pass with two
   profiles, but canonical Bot Chat reads and profile-scoped authorization
   remain closed and unqualified. Only after those read tests pass may an
   exact-tag read-compat entry be added. Send, jobs, model writes, and prompt
   control require separate qualification and remain closed by default.

Until these gates pass, independent device pairing and explicit
`hermes_build_unsupported` responses are the supported behavior on this tag.
